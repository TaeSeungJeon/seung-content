# 커넥션 풀, 왜 필요한가?

먼저 커넥션 풀이란 DB에 쿼리를 날리려면 먼저 커넥션(연결)을 맺어야 한다. 
근데 이 연결을 맺는 과정이 생각보다 비싸다.
```
요청마다 연결 맺을 때
→ TCP 소켓 연결
→ DB 인증 (아이디/비밀번호 검증)
→ 세션 생성
→ 쿼리 실행
→ 연결 종료
```
요청이 100개라고 가정하면 이 과정을 100번 반복 해야하는데, 느리고 DB에 부담이 간다.
커넥션 풀은 이걸 해결하는 방법이다. 
연결을 미리 여러개 만들어 놓고, 빌려쓰고 반납하는 구조라고 생각하면 된다.
```
예를 들어 서버 시작 시 DB 연결 10개를 미리 생성해서 풀(Pool)에 보관

요청이 들어오면
→ 풀에서 연결 하나 빌림
→ 쿼리 실행
→ 연결 반납 (종료 X, 풀로 돌아감)
```

## HikariCP 

커넥션 풀을 구현한 라이브러리 중 하나이다.
"커넥션 풀 = 개념 | HikariCP = 그 개념의 구현체"

HikariCP가 벤치마크 성능에서 압도적이라 Spring Boot 2.0부터 기본값으로 채택됐다고 한다.
즉, **spring-boot-starter-data-jpa** 의존성만 추가하면 별도 설정 없이 HikariCP를 손쉽게 사용할 수 있다.

### 내부 동작 원리

핵심은 `ConcurrentBag`이라는 자체 자료구조다. 일반적인 `BlockingQueue` 대신 이걸 쓰는 이유가 있다.

`ConcurrentBag`은 **Thread-local 캐시**를 먼저 확인한다.  
이전에 같은 스레드가 사용했던 커넥션을 우선적으로 돌려주는 방식이다. 덕분에 락 경합 자체가 줄어든다.

```
스레드 요청
  → Thread-local 캐시에 반납된 커넥션 있나? → 있으면 즉시 반환
  → 공유 풀에서 CAS(Compare-And-Swap)로 획득
  → 없으면 대기 후 신규 생성
```

여기에 **ByteCode 레벨 최적화**까지 적용돼 있다.  
프록시 객체를 직접 바이트코드로 조작해서 리플렉션 오버헤드를 없앤다.  
이게 HikariCP가 다른 풀보다 수십~수백 마이크로초 빠른 이유다.

### 장단점

-  성능은 압도적이고, 설정이 단순하다
-  운영 중 모니터링 기능이 상대적으로 약함
-  인터셉터 같은 확장 포인트 없음

## Tomcat JDBC Pool 비교 이해

Tomcat JDBC Pool은 성능보다 운영 편의성과 확장성에 초점을 맞춘 
오래된 DBCP를 대체하기 위해 만들어진 풀이다.


내부적으로 `FairQueue` 또는 `LinkedList` 기반 큐를 사용한다.  
커넥션 요청이 들어오면 큐에서 순서대로 꺼내 준다.

가장 독특한 기능은 **인터셉터 체인(Interceptor Chain)** 이다.

```
커넥션 요청
  → 인터셉터1 (쿼리 로깅)
  → 인터셉터2 (슬로우 쿼리 감지)
  → 인터셉터3 (커넥션 유효성 검사)
  → 실제 DB 연결
```

각 인터셉터를 직접 구현해서 끼워 넣을 수 있다.  
예를 들어 특정 쿼리의 실행 시간을 측정하거나, 커넥션 상태를 로깅하는 커스텀 로직을 추가할 수 있다.  
JMX 모니터링 기본 지원이라 운영 환경에서 풀 상태를 실시간으로 들여다볼 수 있다.

-  인터셉터로 자유로운 커스터마이징
-  JMX 상세 모니터링 지원
-  성능은 HikariCP 대비 보통
-  설정 복잡도가 상대적으로 높음

## 핵심 비교 정리

| 항목 | HikariCP | Tomcat JDBC Pool |
|---|---|---|
| 성능 |  압도적으로 빠름 | 보통 |
| 설정 복잡도 | 낮음 | 중간 |
| 모니터링 | 기본 제공 | JMX 상세 지원 |
| 커스터마이징 | 제한적 | 인터셉터로 자유롭게 |
| Spring Boot 기본값 |  2.x~ | 예전 기본값 |
| 적합한 상황 | 대부분의 서비스 | 복잡한 운영 요구사항 |

## 그래서 뭘 써야 하나?

대부분의 경우 **HikariCP** 를 압도적으로 많이 사용한다.
Spring Boot 2.0(2018)부터 기본값으로 채택됐고, 설정도 간단하고, 성능도 가장 좋다.
Spring 기반 프로젝트라면 설정 없이 자동으로 HikariCP가 붙고, 
현재 Spring Boot 프로젝트의 대다수가 여기 해당하니 사실상 업계 표준이라봐도 무방하다.

Tomcat JDBC Pool이 빛나는 건 **커스텀 인터셉터가 필요한 복잡한 운영 환경**이다.  
슬로우 쿼리 감지, 커넥션 누수 추적, 세밀한 JMX 모니터링이 필요하다면 그때 고려해볼 만하다.

결국 두 도구 모두 같은 `DataSource` 인터페이스를 구현하기 때문에 교체도 설정 몇 줄로 끝난다.  
구현체보다 **커넥션 풀 자체의 동작 원리를 이해하는 게 더 중요하다**는 게 공부하면서 느낀 점이다.


## HikariCP win !
