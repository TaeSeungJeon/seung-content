## 공부하게 된 계기

이번 블로그 프로젝트에서 JWT를 직접 구현하면서 자연스럽게 의문이 생겼다.

"왜 AWS 환경에서는 세션 대신 JWT를 쓴다는 말을 이렇게 자주 듣는 걸까?"

JWT는 구현했는데 AWS는 아직 제대로 써보지 못한 상황이다.
Oracle Cloud로 배포를 진행 중이지만, 실무에서 AWS는 거의 표준처럼 쓰인다.
이 두 개념을 연결해서 이해해두면 나중에 분명히 도움이 될 것 같아서 이번에 정리해봤다.

---

## AWS란 무엇인가

**AWS(Amazon Web Services)** 는 아마존이 제공하는 클라우드 컴퓨팅 서비스 플랫폼이다.

쉽게 말하면 이렇다.

"서버, 저장소, 데이터베이스, 네트워크 등 IT 인프라를 인터넷으로 빌려 쓰는 서비스"

예전에는 서비스를 운영하려면 서버를 직접 구매하고, 데이터센터를 임대하고,
네트워크를 직접 세팅해야 했다. 초기 비용도 크고, 유지보수도 직접 해야 했다.

AWS는 이 모든 인프라를 클라우드로 제공한다.
필요할 때 켜고, 필요 없으면 끄고, 쓴 만큼만 비용을 낸다.

---

## AWS를 써야 하는 이유

**1. 초기 비용 없이 시작 가능**
서버를 직접 살 필요가 없다. 월 단위, 시간 단위로 사용한 만큼만 비용을 낸다.

**2. 전 세계 어디서든 빠르게**
AWS는 전 세계에 데이터센터(리전)를 보유하고 있다.
사용자와 가까운 리전에 서버를 띄우면 응답 속도가 빨라진다.

**3. 트래픽에 따라 자동 확장**
갑자기 사용자가 몰려도 Auto Scaling으로 서버를 자동으로 늘렸다가 줄일 수 있다.
직접 서버를 늘리는 작업 없이 자동으로 처리된다.

**4. 다양한 서비스 생태계**
단순 서버(EC2)뿐만 아니라 DB(RDS), 저장소(S3), 인증(Cognito),
API Gateway, Lambda 등 수백 가지 서비스를 조합해서 사용할 수 있다.

**5. 실무 표준**
국내외 대부분의 회사가 AWS를 사용한다.
AWS를 다룰 줄 안다는 것 자체가 백엔드 개발자로서의 경쟁력이 된다.

---

## JWT란 무엇인가

**JWT(JSON Web Token)** 는 사용자 인증 정보를 담은 토큰이다.

"서버가 발급해준 신분증 같은 것"

로그인에 성공하면 서버가 JWT를 발급해주고,
이후 사용자는 모든 요청에 이 JWT를 들고 다니면서 "나 로그인한 사람이에요"를 증명한다.

### JWT 구조

JWT는 점(.)으로 구분된 세 부분으로 이루어져 있다.
Header.Payload.Signature
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJUYWVTZXVuZyJ9.abc123xyz

| 부분 | 역할 | 예시 내용 |
|------|------|----------|
| **Header** | 토큰 타입, 암호화 알고리즘 정보 | `{ "alg": "HS256", "typ": "JWT" }` |
| **Payload** | 실제 담긴 데이터 (사용자 정보 등) | `{ "sub": "TaeSeung", "exp": 1234567890 }` |
| **Signature** | 위변조 방지용 서명 | Header + Payload를 비밀키로 암호화한 값 |

Payload는 Base64로 인코딩되어 있어서 누구나 디코딩해서 볼 수 있다.
그래서 **비밀번호 같은 민감한 정보는 절대 넣으면 안 된다.**

Signature가 있기 때문에 누군가 Payload를 조작하면 서명 검증에서 바로 탈락한다.

---

## 세션 방식 vs JWT 방식

인증 방식을 이해하려면 세션과 JWT를 비교해봐야 한다.

### 세션 방식

사용자 로그인
서버가 세션 저장소에 로그인 정보 저장
세션 ID를 쿠키로 사용자에게 전달
이후 요청마다 세션 ID로 저장소에서 정보 조회


서버가 로그인 상태를 직접 기억하고 있어야 한다. → **Stateful**

### JWT 방식

사용자 로그인
서버가 JWT 발급 후 사용자에게 전달
서버는 아무것도 저장하지 않음
이후 요청마다 JWT를 검증만 함


서버가 로그인 상태를 기억하지 않는다. → **Stateless**

## AWS 환경에서 JWT가 더 적합한 이유

AWS 실무 환경에서는 서버가 보통 여러 대 운영된다.
트래픽이 많아지면 Auto Scaling으로 서버를 자동으로 늘리기 때문이다.
사용자 요청
↓
로드 밸런서 (트래픽 분산)
↓             ↓             ↓
서버 A        서버 B        서버 C

### 세션 방식의 문제
1번 요청 → 서버 A에서 세션 생성
2번 요청 → 로드 밸런서가 서버 B로 보냄
→ 서버 B에는 세션이 없음 → 로그인 풀림 

세션은 특정 서버에 저장되어 있기 때문에,
다른 서버로 요청이 가면 세션을 찾을 수 없는 문제가 생긴다.

### JWT 방식의 해결
1번 요청 → 서버 A에서 JWT 검증 
2번 요청 → 서버 B에서 JWT 검증 
3번 요청 → 서버 C에서 JWT 검증 

JWT는 서버가 아무것도 저장하지 않는다.
어느 서버로 요청이 가든 같은 비밀키로 서명만 검증하면 되기 때문에
여러 대의 서버가 있어도 아무 문제가 없다.

이게 AWS 분산 환경에서 JWT가 표준처럼 쓰이는 핵심 이유다.

---

## AWS + JWT 조합의 장점

**1. Stateless — 서버 확장이 자유롭다**
서버가 몇 대든 상관없다. JWT 검증은 어느 서버에서나 동일하게 동작한다.

**2. 서버 부하 감소**
세션 저장소를 조회하는 DB 쿼리가 없다.
비밀키로 서명만 검증하면 되기 때문에 요청 처리가 빠르다.

**3. 마이크로서비스 구조에 적합**
AWS에서는 여러 개의 작은 서비스(마이크로서비스)로 분리하는 경우가 많다.
JWT 하나로 여러 서비스에서 동일하게 인증을 처리할 수 있다.

**4. 모바일 / 프론트 분리 구조에 적합**
이 블로그 프로젝트처럼 프론트와 백엔드가 완전히 분리된 구조에서
쿠키 기반 세션보다 JWT가 훨씬 다루기 편하다.

---

## AWS + JWT 조합의 단점과 주의할 점

장점만 있는 기술은 없다. 반드시 알고 써야 하는 단점들이다.

### 1. 토큰 탈취 문제

JWT가 탈취되면 만료될 때까지 공격자가 그 토큰을 그대로 사용할 수 있다.
세션은 서버에서 즉시 삭제할 수 있지만, JWT는 서버가 상태를 저장하지 않기 때문에
발급된 토큰을 강제로 무효화할 방법이 없다.

대응 방법: Access Token의 만료 시간을 짧게 설정한다. (보통 15분 ~ 1시간)

### 2. 토큰 강제 만료 불가 문제

사용자가 로그아웃해도 서버 입장에서는 토큰이 만료될 때까지 유효하다.

대응 방법: Redis에 블랙리스트를 관리하거나, Refresh Token을 서버에 저장해서 관리한다.

### 3. Payload 노출 문제

JWT의 Payload는 누구나 Base64 디코딩으로 볼 수 있다.
암호화된 게 아니라 그냥 인코딩된 것이기 때문이다.

대응 방법: Payload에 민감한 정보(비밀번호, 개인정보 등)는 절대 넣지 않는다.

### 4. 토큰 크기 문제

세션 ID는 짧은 문자열이지만, JWT는 Payload에 담긴 데이터만큼 크기가 커진다.
매 요청마다 헤더에 JWT를 담아서 보내기 때문에 네트워크 트래픽이 늘어날 수 있다.

---

## Access Token + Refresh Token 전략

JWT의 단점을 보완하기 위해 실무에서는 두 가지 토큰을 함께 사용한다.

| 토큰 | 만료 시간 | 역할 |
|------|----------|------|
| **Access Token** | 짧게 (15분 ~ 1시간) | 실제 API 요청에 사용 |
| **Refresh Token** | 길게 (7일 ~ 30일) | Access Token 재발급 요청에 사용 |

로그인 → Access Token(15분) + Refresh Token(7일) 발급
API 요청마다 Access Token 사용
Access Token 만료
Refresh Token으로 새 Access Token 재발급 요청
서버가 Refresh Token 검증 후 새 Access Token 발급
Refresh Token도 만료되면 → 재로그인


Access Token은 짧게 살아있기 때문에 탈취되어도 피해가 최소화되고,
Refresh Token은 서버(DB 또는 Redis)에 저장해서 강제 만료가 가능하다.

---

## 실무 흐름 예시
[로그인]
사용자 → POST /auth/login
← Access Token (헤더) + Refresh Token (HttpOnly 쿠키)
[API 요청]
사용자 → GET /api/posts
Authorization: Bearer {AccessToken}
← 200 OK
[Access Token 만료]
사용자 → POST /auth/refresh
Cookie: {RefreshToken}
← 새 Access Token 발급
[로그아웃]
사용자 → POST /auth/logout
→ 서버에서 Refresh Token 삭제
← 204 No Content

## 이 블로그 프로젝트와 연결해서 보면

현재 이 블로그는 Oracle Cloud에 백엔드가 올라가는 구조지만,
JWT를 사용하는 이유는 AWS와 동일하다.

프론트(GitHub Pages)와 백엔드(Oracle Cloud)가 완전히 다른 도메인에서 동작하고,
서버가 로그인 상태를 저장하지 않아도 되는 Stateless 구조가 이 아키텍처에 딱 맞기 때문이다.

현재는 Access Token만 사용하고 있는데,
추후 Refresh Token 전략을 추가하면 보안을 한 단계 더 높일 수 있다.

---

## 한 줄 요약

AWS는 인프라를 빌려 쓰는 서비스이고,
JWT는 서버가 아무것도 기억하지 않아도 되는 신분증이다.
여러 대의 서버가 돌아가는 AWS 환경에서 JWT가 표준인 이유는
어느 서버든 같은 방식으로 검증할 수 있기 때문이다.
