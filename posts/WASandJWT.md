## WAS란 무엇 ?

**WAS(Web Application Server)** 는 동적인 요청을 처리하는 서버이다.

WS(Web Server)와 비교해보자

WS는 이미 만들어진 파일을 그대로 돌려주는 역할을 하고,

WAS는 요청이 들어오면 로직을 실행해서 그때 그때 다른 결과를 만들어낸다.

```
사용자 요청
↓
Nginx (WS)       ← 정적 파일은 직접 처리, 동적 요청은 WAS로 전달
↓
Tomcat (WAS)     ← 비즈니스 로직 실행, DB 조회, 응답 생성
↓
DB / 외부 API
```
---
### WAS 사용 방법

일반적인 방식에서는 Tomcat을 따로 설치하고 war 파일로 빌드해서 서버에 직접 올려야 했다.

일반적인 방식    →  Tomcat 설치 → war 빌드 → webapps 배포 → 실행

Spring Boot  →  jar 빌드 → java -jar 실행 → 끝

Spring Boot는 Tomcat을 내장 하고 있어서 jar 파일 하나로 WAS가 함께 실행된다.

---

### WAS의 장단점

WAS는 비즈니스 로직 실행, DB 조회, 외부 API 호출 등 복잡한 요청을 전부 처리할 수 있다.

스레드 풀로 여러 요청을 처리하고, 트랜잭션 관리, 세션 관리 등 실무에서 필요한 대부분의 기능을 지원한다.

반면 정적 파일 처리는 WS보다 느리고,

스레드 풀, 커넥션 풀, 타임아웃 등 튜닝해야 할 항목이 많다.

**잘못 건드리면 성능 저하나 장애로 직결된다.**

그리고 WAS 하나가 죽으면 그 서버로 오는 요청 전체가 영향을 받기 때문에

**WAS를 여러 대 띄우는 이중화 구성을 쓰자**

## JWT란 무엇 ?

**JWT(JSON Web Token)** 

로그인 성공 시 서버가 발급하는 **인증 토큰**이다.

생김새는 이렇다.
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJUYWVTZXVuZyJ9.abc123xyz

점(.)으로 구분된 세 덩어리로 이루어져 있다.

| 부분 | 내용 | 역할 |
|------|------|------|
| **Header** | `{"alg": "HS256", "typ": "JWT"}` | 암호화 알고리즘 정보 |
| **Payload** | `{"sub": "TaeSeung", "exp": 1234567890}` | 실제 담긴 사용자 데이터 |
| **Signature** | Header + Payload를 비밀키로 서명한 값 | 위변조 방지 |

**Payload는 암호화가 아니라 Base64 인코딩이다.**

누구나 디코딩해서 내용을 볼 수 있기 때문에

민감한 정보(비밀번호, 개인정보 등)는 절대 넣으면 안 된다.

Signature가 있기 때문에 누군가 Payload를 조작하면
서명 검증에서 바로 탈락한다. 이게 위변조 방지가 되는 원리다.

---
### JWT 사용 방법

JWT의 핵심은 **서버가 아무것도 저장하지 않는다**는 것이다.

세션 방식과 비교하면 차이가 명확하다.

**세션 방식**
로그인 → 서버가 세션 저장소에 로그인 정보 저장

요청마다 → 세션 ID로 저장소 조회 → Stateful

**JWT 방식**
로그인 → 서버가 JWT 발급 후 클라이언트에 전달 (서버는 저장 안 함)

요청마다 → JWT 서명만 검증 → Stateless

실제 요청 흐름
```
로그인 성공
↓
서버가 JWT 발급 → 클라이언트 저장 (localStorage 등)
↓
이후 모든 API 요청
↓
Authorization: Bearer {JWT} 헤더에 포함
↓
서버가 서명 검증 → 인증 완료
```
### JWT의 장단점

서버가 상태를 저장하지 않으니 서버가 몇 대든 상관없다.

어느 서버로 요청이 가도 같은 비밀키로 검증하면 끝이다.

세션 저장소를 조회하는 DB 쿼리가 없으니 처리도 가볍고,

프론트와 백엔드가 완전히 분리된 구조에서 특히 잘 맞는다.


**JWT가 탈취되면 만료될 때까지** 공격자가 그대로 사용할 수 있고,

사용자가 로그아웃해도 토큰은 만료 전까지 살아있다.

서버가 상태를 저장하지 않기 때문에 강제로 무효화할 방법이 없다.

## WAS와 JWT가 만났을 때

### 세션의 한계

WAS를 여러 대 띄우는 이중화 구성에서 세션을 쓰면 이런 문제가 생긴다.
```
1번 요청 → WAS A에서 세션 생성
2번 요청 → 로드 밸런서가 WAS B로 전달
→ WAS B에는 세션이 없음 → 로그인 풀림 
```
세션은 특정 서버 메모리에 저장되기 때문에
다른 서버로 요청이 가면 세션을 찾을 수가 없다.

Redis 같은 공유 세션 저장소로 해결할 수는 있지만
구조가 복잡해지고 관리 포인트가 늘어난다.

### JWT가 만드는 환경

JWT는 이 문제를 구조적으로 해결한다.
```
1번 요청 → WAS A에서 JWT 검증 
2번 요청 → WAS B에서 JWT 검증 
3번 요청 → WAS C에서 JWT 검증 
```
서버가 아무것도 저장하지 않으니

어느 WAS로 요청이 가도 같은 비밀키로 서명만 검증하면 된다.

WAS가 Stateless한 JWT를 만나면

서버를 아무리 늘려도 인증 로직이 흔들리지 않는 구조가 된다.

---
### 이 조합의 약점

이 조합에도 한계는 있다.

토큰 탈취 문제는 여전히 남아있고,

Refresh Token을 여러 WAS에서 어떻게 공유할지

전략을 제대로 세우지 않으면 오히려 복잡해질 수 있다.

이런경우 두 토큰 전략으로 이 약점을 커버한다.

```
로그인
→ Access Token (짧게) + Refresh Token (길게) 발급
→ API 요청마다 Access Token 사용
→ Access Token 만료 시 Refresh Token으로 재발급
→ Refresh Token도 만료 시 재로그인
```
Access Token이 탈취돼도 금방 만료되어 피해가 최소화되고,

Refresh Token은 서버(DB 또는 Redis)에 저장해서 강제 삭제가 가능하다.

로그아웃 문제도 여기서 해결이된다.

---

## 다른 인증 방식과 비교했을 때

인증 방식은 JWT 말고도 여러 가지가 있다. 대표적으로 세션, OAuth, API Key 방식이 있는데

각각 어떤 상황에 맞는지 알고 나면 왜 JWT가 자주 선택되는지 이해가 된다.

| 방식 | 특징 | 적합한 상황 |
|------|------|------------|
| **Session** | 서버가 상태 저장, 강제 만료 가능 | 단일 서버, 관리자 페이지 등 |
| **JWT** | Stateless, 서버 확장 자유로움 | 분리된 프론트/백엔드, 다중 서버 |
| **OAuth** | 외부 서비스 인증 위임 | 소셜 로그인 |
| **API Key** | 단순한 키 기반 인증 | 서버 간 통신, 외부 API |

---
### 선호되는 이유

가장 큰 이유는 **확장성**이다.

서버가 늘어나도 인증 로직을 건드릴 필요가 없다.

세션처럼 공유 저장소를 따로 관리하지 않아도 되고,

어느 서버로 요청이 가든 비밀키 하나로 검증이 끝난다.

두 번째는 **구조적인 유연함**이다.

프론트와 백엔드가 완전히 분리된 구조, 모바일 앱, 마이크로서비스처럼

다양한 클라이언트가 같은 서버를 바라보는 환경에서 

쿠키 기반 세션보다 JWT가 훨씬 다루기 편하다.

세 번째는 **자기 완결성**이다.

토큰 안에 사용자 정보가 담겨 있어서

별도의 DB 조회 없이 토큰 하나만으로 인증이 완결된다.

이게 응답 속도에도 직접적인 영향을 준다.

---
### 저평가 되는 이유

반면 JWT가 과대평가됐다는 시각도 분명히 존재한다.

가장 큰 이유는 **강제 만료가 불가능**하다는 점이다.

세션은 서버에서 즉시 삭제할 수 있지만

JWT는 한번 발급되면 만료 시간 전까지 막을 방법이 없다.

보안이 중요한 서비스에서는 이게 치명적인 약점이 될 수 있다.

두 번째는 **Payload 노출 문제**다.

암호화가 아니라 인코딩이기 때문에 누구나 내용을 볼 수 있다.

이걸 모르고 민감한 정보를 담으면 보안 사고로 이어진다.

세 번째는 **토큰 크기**다.

세션 ID는 짧은 문자열이지만 JWT는 Payload가 커질수록 토큰도 커진다.

매 요청마다 헤더에 담겨서 오가기 때문에

트래픽이 많은 서비스에서는 이게 무시할 수 없는 오버헤드가 된다.

마지막으로 **Refresh Token 전략을 제대로 구현하지 않으면**

결국 서버에 상태를 저장하게 되면서 Stateless의 장점이 희석된다.

JWT를 쓰는 이유가 Stateless인데, 그 장점을 제대로 살리려면

설계가 생각보다 꼼꼼해야 한다.

---
### 결국 JWT는 만능 해결책이 아니다.

확장성과 편의성을 얻는 대신 강제 만료와 보안 관리를 직접 책임져야 한다.

이걸 알고 쓰는 것과 모르고 쓰는 것은 완전히 다른 이야기다.

---

## 한 줄 요약

WAS는 비즈니스 로직을 처리하는 서버이고, JWT는 서버가 아무것도 저장하지 않아도 되는 인증 방식이다.

이 둘이 만나면 서버가 몇 대로 늘어나도 인증 로직이 흔들리지 않는 구조가 된다.

세션은 특정 서버에 묶이지만, JWT는 어느 WAS로 요청이 가든 같은 비밀키로 검증하면 끝이다.

다만 Stateless라는 편리함 뒤에는 토큰 탈취와 강제 만료 불가라는 구조적 한계가 따라온다.

그래서 Access Token은 짧게, Refresh Token은 서버에 저장해서 관리하는 전략이 필요하다.

개념으로만 알던 것들이 직접 구현하면서 하번씩 손에 익기 시작했고,

알면 알수록 설계가 왜 그렇게 되어있는지 이유가 보이기 시작했다.

**토큰 탈취와 만료 전 로그아웃 문제**를 주의하고,

**Access Token + Refresh Token** 같은 이중 토큰 구조나

**Redis 블랙리스트** 같은 무효화 전략을 함께 사용하자.
